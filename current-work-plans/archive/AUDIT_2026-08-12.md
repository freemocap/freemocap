# Audit — 2026-08-12 · Plans vs. Implementation

> **What this is.** A checkpoint audit of the streaming-compatibility work in progress: the plans in this
> folder read against the code landed on `development-streaming` in `freemocap` / `skellyforge` /
> `skellytracker`. It records *findings*, not decisions — nothing here supersedes a spec doc. Items that
> become decisions move into the doc that owns them ([`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) for
> scope, the numbered docs for design) and this file is left as the dated record of what was found when.
>
> **Convention for this file type:** `AUDIT_<YYYY-MM-DD>.md`, one per audit pass, never edited after the
> follow-up actions land — supersession is recorded by the *next* audit, not by rewriting this one.
>
> **Frame:** this is a refactor in progress. Unfinished work is not a defect. The questions asked were:
> do the plans still describe the work accurately, is the strategy sound, and is anything *committed*
> actually wrong.

---

## Verdict

**The strategy is sound and the mid-course sequencing correction was the right call. The problem is that
the correction was recorded in one document and not propagated, and SF-SH-6 (the "update the specs"
workstream, marked *continuous*) is the one workstream that hasn't run.**

Almost every drift item below traces to that single cause. Six docs describe a plan the work has moved
past, and two of them will actively mislead whoever picks up FMC-WS-2 next.

Separately there is **one genuine correctness bug** in committed, DONE-marked math ([§3.1](#31-local-quaternion-composition-order))
and **one real plan gap** that will get baked in by the next workstream if it isn't closed first
([§2.1](#21-landmark-vs-bone-the-specs-contradict-each-other)).

## 2. Where the plans are underspecified

Missing decisions, not incomplete work.

### 2.1 Landmark vs. bone: the specs contradict each other

The docs are careful about the keypoint / landmark / bone vocabulary
([13](13-tracker-to-canonical-mapping.md)). The channel specs are not consistent with it:

| Doc | Skeleton `POINTS` names | `OVERLAY_2D` names |
|---|---|---|
| [09](09-standard-stream-protocol.md) § channels | *"named 3D landmarks"* | *"per-camera 2D projection of the **tracked landmarks**"* |
| [01](01-canonical-data-model.md) § what the frame carries | *"Rigidified canonical body+hand joints, from `RealtimeSkeletonRigidifier`"* (landmarks) | — |
| [`phase-1/03`](phase-1/03-canonical-frame-extensions.md) (the executable plan) | `names=bone_names` | `names=bone_names` |
| code (`stream_schema.py`) | `bone_names` | `bone_names` |

The code follows the executable plan — the right instinct — but that plan silently overrode two design
docs, and nobody has decided which is authoritative.

It matters concretely: `RealtimeSkeletonRigidifier` emits **27 canonical landmarks**; the standard human
is defined in **bones** (21 in the current bootstrap, 55 at target). Those sets are not the same and never
will be. FMC-WS-2's `StreamSample.from_aggregator_output()` is the code that has to bridge them, and
**no plan document says who owns that mapping or where it lives.** Cheap to decide now; expensive once the
encoder and the UI decoder both hardcode a block layout.

Separately: 2D overlays genuinely *are* tracker keypoints — that is what a camera sees. Keying them by VRM
bone name is very likely just wrong, independent of the above.

### 2.2 Where the canonical bone definition lives — an unresolved `TBD` answered by default

[`phase-1/standard-human-model/README.md`](phase-1/standard-human-model/README.md) § "File structure":

```
└── (standard_human.yaml        # TBD — or defined purely in Python)
```

That TBD was never closed. In its absence the only `StandardHuman` instance in the system is built inline
by `_get_standard_human()` in `freemocap/core/pipeline/realtime/realtime_aggregator_node.py` — a 21-bone
bootstrap, correctly flagged as temporary in [`phase-1/HANDOFF.md`](phase-1/HANDOFF.md) known-issue #4.

What is *not* tracked: **the model currently lives in the wrong repo.** The boundary rule is unambiguous —
*"SkellyForge takes mapped canonical landmarks → builds the standard human (bones, hierarchy, T-pose,
orientations)"*. FreeMoCap defining the canonical human, even provisionally, inverts it. No plan contains a
task to move the definition into SkellyForge and close the YAML-vs-Python TBD — and that task is the actual
blocker for SF-SH-1's definition-of-done.

### 2.3 The plans have no testing strategy for the SkellyForge engine

[08](08-testing-strategy.md) is thorough — for the *wire*: golden bytes, loopback, converter vectors, LSL
pass-through, third-party conformance. It says nothing about the kinematics engine.

The two places that ask for engine tests are:

- `standard-human-model/README.md` § Definition of done — *"`bs/`-parity unit tests on quaternion /
  reference-geometry math"*
- `FMC-WS-5` checklist item 1 — *"5a engine copy-in **+ unit tests** (quaternion math, reference geometry)"*

Neither is satisfied. `skellyforge` has no test infrastructure at all (`pytest` collects nothing; the only
`test_*.py` is an unrelated pipeline file). Roughly 3,200 lines of new math in `skellyforge/kinematics/` +

tests all cover the msgspec/numpy round-trip.

The gap is structural: **doc 08 doesn't own this, so nothing does.** It is what let [§3.1](#31-local-quaternion-composition-order)
through. Worth a section in [08](08-testing-strategy.md), or a sibling doc, naming the engine suite as a
first-class deliverable with an owner.

### 2.4 Open decisions that are now blocking, not merely open

- **Forward-axis.** `FREEMOCAP_CANONICAL_CONVENTION` carries `# TODO(convention): confirm`;

## 3. Actual errors in committed work

Two. One matters.

### 3.1 Local quaternion composition order

**`skellyforge/kinematics/orientation_solver.py:364-366`** — SF-SH-4, marked ✅ DONE.

```python
# local = world_child * conj(world_parent)
parent_conj = parent_world.conjugate()
local = world * parent_conj
```

Derivation, from this codebase's own stated conventions:

1. `RotationQuaternion.rotate_vector` implements `v' = q v q*` — a quaternion maps a vector *from* the
   frame it is expressed in *into* the frame it rotates to.
2. `compute_rotation_from_live_basis` docstring: *"the rotation that takes a bone from its T-pose reference
   orientation to its current live orientation"* — so `q_world` maps bone-T-pose-frame → world.
3. `__mul__` docstring: *"`R(q₁·q₂) = R(q₁) ∘ R(q₂)`"* — `q₂` applied first.

Therefore `q_child_world = q_parent_world ∘ q_local`, which inverts to
**`q_local = conj(q_parent_world) * q_child_world`** — the opposite operand order from the code.

Verified numerically (parent = 90° about Z; true local = 90° about X):

| | w | x | y | z |
|---|---|---|---|---|
| true local | +0.7071 | **+0.7071** | 0 | 0 |
| `world * conj(parent)` (code) | +0.7071 | 0 | **+0.7071** | 0 |
| `conj(parent) * world` | +0.7071 | **+0.7071** | 0 | 0 |

Right angle, wrong axis. The code's expression is the delta *expressed in world frame*; parent-relative
requires the other order.

**Two reasons this needs more than a one-line fix.**

First, `ROTATIONS_LOCAL` is exactly what VMC and Unreal consume, and
[07 — The local-rotation trap](07-coordinate-conventions.md#the-local-rotation-trap-vmc-and-unreal) names
this as *"the single most common VMC implementation bug (it produces a memorable explosion)."* The spec
identified the trap and the implementation stepped in it — a signal about the review loop, not just the
line.

Second: **the test that passed cannot have caught it.** The SF-SH-4 progress note cites *"90 deg bend
(correct world quats + **identity local for uniform bend**)."* In a uniform bend `q_child == q_parent`, so
`q_c · conj(q_p)` and `conj(q_p) · q_c` both reduce to identity. The test is structurally blind to operand
order. The fix must land with a **differential** case — parent and child rotated by different amounts about
different axes — plus a round-trip assertion (`recompose(parent, local) == child`) that pins the convention
rather than sampling it.

If the derivation is wrong, the place it is wrong is step 2 — if `q_world` is intended as world→bone rather
than bone→world. That needs confirming directly, because it also determines what the Phase-3 VMC adapter
must do. **Either way it should be written into [07](07-coordinate-conventions.md) as an explicit stated
convention.** It is currently inferable from three docstrings and stated nowhere.

### 3.2 The damping fallback disables damping

`_solve_chain_resolved` calls `_solve_damped_minimal(..., previous_world_quaternion=None)` on both fallback
paths (twist source missing; singularity gate tripped). With `previous=None`, `_solve_damped_minimal`
returns `current` unsmoothed — so the exact situation damping exists for receives none, and will pop.

[12](12-standard-human-model.md) specifies the opposite: *"when the twist source is occluded, hold
zero/rest twist and **temporally damp** it … to avoid jitter/pop."*

Related: `slerp(previous, current, 1.0 - 0.95)` weights the previous frame at 95% — a first-order lag with
a ~0.33 s time constant at 60 Hz. Both [12](12-standard-human-model.md) and `TwistPolicy`'s docstring call
it "critically damped," which is a different thing and sets the wrong expectation for tuning.

## 6. Strategy assessment

**The bet is good.** One LSL-shaped standard stream in the middle, thin transports, foreign adapters
derived — the asymmetry argument in [00](00-overview.md) ("a same-shape transport is a pass-through; a
foreign protocol is a bone-name map plus a byte layout") is the correct reason to build it this way, and
the reason adding VMC later won't be a research project.

Right, and not to be second-guessed:

- **Convention-as-schema-fact** ([07](07-coordinate-conventions.md)), and the local-rotation-trap section —
  institutional memory that usually only exists *after* shipping the bug.
- **The wire contract** — self-describing blocks, no per-frame names, first-class timestamp, header/footer
  integrity check, first-byte demux that doesn't collide with skellycam's image protocol. It genuinely
  flattens to `push_sample`.
- **Declarative `TwistPolicy`** — putting the underdetermined-roll decision in data rather than in solver
  branches is what makes the per-bone tiers auditable.
- **The tracker→canonical boundary** ([13](13-tracker-to-canonical-mapping.md)) and `anatomical_offset` as
  a fourth mapping form — deterministic, subject-scaled, never runtime-fit.
- **Copy-don't-import for `bs/`**, and "SkellyForge never imports FreeMoCap."
- **The reversal itself.** Designing a stream around data not yet produced is how you get a schema that
  can't carry what you eventually need. The resulting schema (five groups, both rotation frames, per-camera
  overlays) is visibly better for having had the model to build against.

**The one strategic risk** is [§2.1](#21-landmark-vs-bone-the-specs-contradict-each-other): the
landmark/bone impedance mismatch is unnamed, and FMC-WS-2 + FMC-WS-4 will both hardcode a block layout
against it. That decision belongs before the next line of encoder code, not after.
