# Recording folder and run contract

The maintained target now lives in [RECORDING_CONTRACT.md](../../RECORDING_CONTRACT.md).
This document is the dated implementation audit, not a second normative contract.
The first implementation stage adds lazy `exports_dir`/`exportsDir` path support
and shared path parity tests. Subsequent work adds version-1 stage provenance in
the existing processing envelope, saved defaults, restart invalidation and real
test/sample-data acceptance. The outer descriptor remains schema 1. The audit
below describes the starting state; see the maintained contract for current
coverage and limitations. Writer migration remains pending.

Audit and alignment plan, 2026-09-30. This document distinguishes implemented
behavior from pending changes. It records the folder/provenance findings for
the secondary-export work; older layout and JSON-mirror claims are historical.
No recording migration or runtime schema change was performed by this audit.

## Authorities and identities

- Recording identity is the folder name (`recording_name` / `recording_id`). A
  capture UUID can coexist as capture metadata; it is not a replacement path ID.
- Capture metadata describes cameras, media associations and timing at acquisition.
  Processing must preserve it. It is not the configuration of every processing run.
- `<id>_data.parquet` is the authoritative processed dataset. Its embedded
  `freemocap.recording` descriptor contains `selected_run_id` and `runs`, and every
  numerical row carries `run_id`. There is one Parquet across retained runs.
- Each run owns its sources, models, clocks, reference frames, camera geometry,
  scale fits, processing reports, channel declarations and checkpoint signatures.
- Export files are derived snapshots. Their run ID plus source revision/hash
  identifies what was exported; a filename alone cannot prove freshness.
- A run ID is a retained result slot, not an immutable revision or an attempt ID.
  Overwrite can change its contents. Keeping a new run allocates another ID.

## What is actually written today

The backend `RecordingStructure` and frontend layout presets declare
`videos/synchronized`, `videos/annotated`, `<id>_recording_info.json` and
`<id>_calibration.toml`. Several active writers still use other names:

| Content | Current writer / location | Scope |
| --- | --- | --- |
| Capture video | SkellyCam `RecordingInfo.videos_folder`; synchronized-video layout supported alongside canonical layout | Recording |
| Capture JSON | SkellyCam writes `<id>_info.json`, with camera configs, recording UUID/start time, media and timing associations | Recording |
| Capture timing | Capture sidecars referenced by capture JSON, including group/per-camera timing and statistics | Recording |
| Optional audio | WAV and audio timestamp JSON in the capture video folder | Recording |
| Board input | Reference datasets retain `charuco_board_info.json` | Input |
| Calibration TOML | Calibration save helper writes `<id>_camera_calibration.toml`; mocap can copy a selected calibration under its original basename | Calibration result/input |
| Scientific output | `<id>_data.parquet`, with numerical rows and embedded run descriptors | All retained runs |
| Annotated video | Separate annotated-video folder; current reference outputs use `annotated_videos/` | Derived; no general per-run retention contract |
| Diagnostics | `output/diagnostics.yaml`, regenerated by Parquet publication | Derived report |
| Observation cache | `output_data/charuco_observations_realtime.pkl` in the realtime board-cache path | Reusable cache, not canonical scientific output |
| Logs | `logs/` is declared; dataset workflow also saves logs outside the recording under its attempt directory | Attempt/tool dependent |
| Blender | Existing exporter defaults to `<id>.blend` at recording root | Derived legacy output |
| Lock/scratch | `.processing.lock` and temporary `.parquet.tmp` files at publication | Operational, not retained results |

The two prepared reference recordings inspected have legacy video/calibration
names, a root Parquet and `output/diagnostics.yaml`. Neither contains a capture
recording-info JSON. Their embedded `recording_info` fields are empty. This is
consistent with imported reference inputs, not evidence that live capture never
saves camera information.

Dataset `ready.json`, `attempts/` and `history/` live outside those recording
folders. They retain useful workflow/configuration/version information, but are
test-data preparation infrastructure, not a portable general recording contract.

`publish_recording` validates and atomically replaces Parquet, then regenerates
diagnostics. It does not mirror the run descriptor into recording-info JSON.
The guide in `freemocap/core/recording/recording_guide.md` reflects this separation.
Older plans claiming an authoritative JSON dataset mirror/recovery are stale.

## What is saved about parameters and runs

Implemented:

- Full mocap processing saves `task_config.model_dump(mode='json')` in tracker
  source definitions. This includes materialized configuration defaults, not just
  changed fields, along with the resolved tracker configuration at publication.
- Filtering stores its actual config plus gap-filling and filter reports in
  `run.processing[group].filtering`. Filtering restarts replace this report.
- Models preserve scientific skeleton/rest-pose/mapping/mass definitions; scale
  fits preserve fitted values and their input binding. Playback/reconstruction
  need not infer these from today's installed skeleton defaults.
- Camera geometry used for triangulation and alignment update records are saved
  per run/group. Calibration TOML additionally contains board/solver statistics
  and alignment history, but is not a complete per-run configuration archive.
- Storage/planner support keep/overwrite: `keep=True` allocates `max(runs)+1`,
  copies reusable data and retains the original. The ordinary mocap config has
  no keep option; saved-stage execution currently targets `base_run_id` in place.
  Do not describe app-wide keep as done.

Gaps:

- There is no uniform stage-scoped record of the effective settings, software
  identity, execution time and parent result revision for each published output.
- A retained tracker definition describes the observations that produced it.
  Later filtering/retriangulation must not be represented by that original whole
  task config. Saved observation reuse deliberately retains detector provenance;
  newer stage settings are not uniformly captured elsewhere.
- No persisted defaults baseline or reliable user-choice origin distinguishes
  an explicitly selected setting from an inherited default. Comparing against
  current defaults later would give incorrect historical answers.
- Checkpoint signatures establish input/output compatibility but do not explain
  every original parameter. A hash cannot replace a readable configuration.
- Run IDs/selection are saved, but typed run creation/lineage metadata is absent.
- Annotated videos, root calibration convenience files, logs and diagnostics do
  not all have retained-run artifact identities. Keeping Parquet runs does not
  automatically retain matching versions of all side files.

## Agreed export placement

```text
<id>/
    <id>_data.parquet
    ...capture media, metadata, calibration and diagnostics...
    exports/
        <id>.tall.csv
        <id>.landmarks.wide.csv
        <id>.npz
        <id>.metadata.json
        run-0/
            <id>.run-0.tall.csv
            <id>.run-0.landmarks.wide.csv
            <id>.run-0.npz
            <id>.run-0.metadata.json
```

Only requested formats exist. Default exports replace selected formats directly
under `exports/`. Explicit retention puts the same outputs in `run-<id>/` and adds
the run ID to filenames. Normal export never overwrites retained files; an existing
retained destination cannot be silently replaced. Retention must bind the folder
to one source run revision, preventing later additions from mixing revisions.

`<id>.metadata.json` combines the export manifest and a snapshot of the recording
descriptor. It is a derived sidecar, not the recording's new source of truth.
NPZ embeds the same interpretation information. Track provenance per artifact,
because exporting only NPZ must not relabel an older CSV as current. Preserve the
descriptor snapshots referenced by retained/stale artifacts. File hashes detect
interrupted publication of a multi-file set; multiple replacements are not one
atomic filesystem transaction.

Saving an export snapshot does not create a new scientific run or guarantee that
its original Parquet revision remains retained. Processing retention and export
retention are separate user choices. Do not use exports as processing checkpoints.

## Bounded alignment work before export integration

1. **Path ownership:** add `exports_dir` to backend structure, frontend structure
   and all layout presets together, created on demand. Keep `output/` for current
   diagnostics/internal artifacts. Route new export paths through this boundary.
   Inventory and test actual capture/media/calibration resolution, including
   hybrid layouts; do not migrate or rename user files automatically. Consolidate
   canonical writer naming separately, with an explicit compatibility strategy.
2. **Stage provenance:** add versioned typed provenance to the existing embedded
   run descriptor. Record effective stage settings including defaults, actual
   algorithm/software identities, relevant input fingerprints, publication time,
   and reuse/parent revision references. Preserve upstream provenance on restarts;
   replace/invalidate downstream provenance with its data in the same publication.
   Preserve calibration input identity and relevant configuration alongside the
   geometry, rather than depending on an old absolute TOML path.
3. **Defaults comparison:** snapshot the applicable default settings at execution
   time (or reference an immutable saved baseline) and derive differences from
   that baseline. Store the submitted request separately from resolved settings
   where useful. Do not label a serialized value as a deliberate user edit merely
   because the frontend sent it. Explicit user-edit attribution requires UI support.
4. **Run semantics:** expose existing keep/overwrite intentionally if needed for
   this milestone; otherwise make overwrite behavior clear. Add lineage metadata
   when allocating a run. Export selection reads existing IDs, never invents them.
   Legacy descriptors remain readable with provenance marked unknown/partial;
   never fill historical gaps with current defaults. Choose schema-version and
   reader compatibility together before implementation.
5. **Artifact publication:** per-recording export lock, owned staging, safe default
   replacement, no-clobber retained publication, per-file hashes/status/revision,
   recovery from interruption and stale-artifact detection. Never modify capture
   JSON or scientific Parquet merely to publish an export.

Acceptance uses temporary recording copies: a full run; a filter-only restart with
changed cutoff while retaining detector settings; keep/overwrite; selected-run
switching; legacy metadata; default versus retained exports; interrupted multi-file
publication; and a moved recording whose numerical interpretation works without
historical absolute paths. This is targeted alignment of existing architecture,
not a new storage system. Blender placement and annotated-video retention remain
explicit follow-ups; the CSV/NPZ task does not silently relocate them.
