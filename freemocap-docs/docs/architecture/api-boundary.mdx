# Server API boundary

This reference targets the integrated `sfn26` runtime `90cd474e`, recorded by
handoff commit `19acf12c`. It is not a claim that every released server with the
same application version exposes these operations. SDK implementation and public
compatibility acceptance are in progress.

HTTP controls the server and reads resources. `/websocket/connect` carries live
frames, application state, logs, framerate reports and task progress. Recorded
playback uses HTTP, with client-owned play/pause/seek; there is no playback
WebSocket session. Electron process launch and OS integration are separate from
the running server API.

The running server's `/openapi.json` describes public HTTP requests and schemas.
Registered hidden compatibility and utility routes must also be inventoried;
OpenAPI does not describe bidirectional WebSocket messages. See the
[WebSocket contract](/docs/architecture/backend-websocket-server).

## Identity, commands and errors

A recording's folder name and optional `recording_parent_directory` identify its
location. Preserve the parent in requests, returned resource URLs and cache keys.
Capture UUID, task ID, retained run ID and content revision are distinct. A run
can be overwritten; a run ID does not identify immutable content.

Exports accept `channels`, `tall_csv` or `blender` requests and return HTTP 202
with a task reference. Artifact inventory persists independently of task-registry
retention. Canonical names are `ExportOptions`, `ExportRequest`, `ExportResult`,
`data_channels` and `DataProvenance`/`data_provenance`.

Task observation uses the shared HTTP/WebSocket registry. Request cancellation
only cancels the client's request; server task cancellation is an explicit command.
An accepted cancellation is not proof the task reached terminal cancellation.
Do not blindly retry commands that create recordings, tasks or exports.

Handle validation, not-found, busy-owner and stale-revision responses explicitly.
Playback bundles can contain usable resources alongside individual resource errors.
Binary assets must preserve their response content type, range headers and response
lifetime; an inferred JSON response schema is not proof that an asset is JSON.
A server filesystem path in an export result is not automatically a downloadable URL.

## Compatibility and utilities

Canonical SDK methods use the recording/capture/import/task routes above, not
hidden `/exports/scientific`, `/mocap` or old recording `/playback` aliases.
Those aliases remain server compatibility behavior. No support for older server
versions is implied by their existence.

`GET /openapi.json` is schema introspection. The hidden playback viewer and explicit
`GET /freemocap/playback/parquet?path=...` utility remain available for their
existing consumers; they are classified separately from recording-based reads.
Root navigation, favicon and generated Swagger/ReDoc pages are server UI resources.

Both ONNX queries are supported: advertised providers and loaded session providers
answer different questions. The latter currently returns `list[dict]`; consumers
must not infer a fixed object shape from one observed session.

## Architecture and evidence

The SDK owns client transport and language-native access, not capture, detector
recipes, mapping evaluation or reconstruction. Component schemas remain owned by
their components. Core owns composition and cross-component API contracts.

See the [accepted integration handoff](https://github.com/freemocap/freemocap/blob/19acf12c68d008e0250fd8921b2d468f996a47a4/current-work-plans/03-transport/api-integration-handoff.md), [route migration](https://github.com/freemocap/freemocap/blob/19acf12c68d008e0250fd8921b2d468f996a47a4/current-work-plans/03-transport/api-route-migration.md), and [recording contract](https://github.com/freemocap/freemocap/blob/19acf12c68d008e0250fd8921b2d468f996a47a4/RECORDING_CONTRACT.md).
