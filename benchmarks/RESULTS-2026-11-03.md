# Mac mini baseline — 2026-11-03

Apple M4 Pro, 12 CPU cores, 16 GPU cores, 24 GiB RAM; macOS 26.6.2; Python 3.12.14.
Tracking used CPUExecutionProvider for RTMW and YOLOX. Other agents and desktop apps were active; AC power, cached model assets, no controlled thermal warmup. These are shared-desktop CPU measurements, not GPU or idle-machine results.

## Physical camera

Existing extended camera suite; one attached A68-1600W, requested 30 fps. Both owned servers exited with code 0 and no cleanup errors.

| Backend / case | Result | Measurement |
|---|---|---|
| Python, 1280×720 recording | Failed requested-FPS acceptance | 19.93 recorded fps; 101 decoded frames; no missing frame numbers |
| Python, resolution change to 640×480 | Resolution-control check passed | 19.85 source fps, below requested 30 fps |
| Python, extended suite | 9/14 passed | Five failures listed below |
| Rust, extended suite | 0/14 passed | Device enumerated, but native opening returned `No cameras detected` |

Python failures: recording FPS acceptance; close-during-recording acceptance; changing to Rust; requested manual exposure not applied; repeat-record-start timed out waiting for pause. Passing cases: pause/resume, repeat apply, stream reconnect, rotation, auto exposure, recommended exposure, resolution change, stop without recording, pause during recording.

The Rust log includes a native camera permission request. The measurements do not establish its root cause or attribute the Python FPS shortfall to CPU performance. Camera/driver/configuration and native permission behavior require a separate diagnosis. No production behavior was changed to make tests pass. The suite executed 720p and its 480p transition; it did not execute the Cartesian planner’s 1080p or every codec combination. No multi-camera hardware was available.

## Reproduction and limits

- [Commands and record format](README.md); [portable records](results/); [verified machine inventory](machines/mac-mini-m4-pro-24gb.json).
- Base Core revision: `5b6adb51`, local `sfn26`; isolated branch `sfn26-machine-benchmarks`. Dependency source locations, revisions, dirty hashes and versions are recorded per run. Core’s cached remote was nine commits ahead; it was not pulled into this benchmark.
- Original Core and SkellyCam checkout branches and user lockfile changes were preserved. Only Core owns changes: the camera harness tested here is Core’s integration harness using SkellyCam public routes.
- Blender 5.2.1 was inspected successfully outside the sandbox, but no FreeMoCap add-on was installed. Blender installation/export/validation were not performed; these numerical results must not be compared against the standard Blender profile.
- Model caches were reused, but each measured run recalibrated and processed every frame in a fresh output directory. Existing outputs could not satisfy validation.
- Dataset system queries reported generic `arm` CPU text; the separately captured unsandboxed inventory identifies this same machine as M4 Pro.
- No Windows measurement archive was available. This is the first machine baseline; comparison software is tested with synthetic cases and actual Mac repetitions, not a claimed Mac-versus-Windows speedup.
- Full logs and recordings remain local under `.test-artifacts/machine-benchmarks/`; only portable records and this summary are versioned. Source JSON is unchanged; Markdown summaries are rendered from it.
