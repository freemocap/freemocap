# Blender Export

FreeMoCap exports a processed recording through a self-contained package installed
in the selected Blender runtime. Blender uses its own bundled dependencies; core
never injects its Python environment or installs packages during export.

## Set up Blender

1. Select a Blender executable in the Blender settings. Windows autodetection also
   checks stable installations managed by Blender Launcher.
2. Choose **Check Blender package**. A package installed in another Blender
   version or in a private VS Code development profile is not necessarily available
   to this runtime's normal profile.
3. If needed, close that Blender instance, expand **Install bundled add-on ZIP**,
   enter the full path to a trusted, built FreeMoCap package, and install it.
   Use a package matching Blender's Python version, OS and architecture.
   Raw repository ZIPs do not contain the required dependencies.
4. If multiple FreeMoCap packages are enabled, select the intended package.

Blender 4.2 and newer support Extension packages. Earlier Blender versions use
legacy add-on packages with privately bundled dependencies. Installation is an
explicit action that saves preferences for the selected Blender runtime. Export
never downloads dependencies. Package inspection and installation use background
Blender processes; installation is verified again in a fresh process.

## Choose the import route

| Route | Input and behavior |
| --- | --- |
| Automatic | Uses saved Parquet segment poses when a recording Parquet exists; otherwise legacy NPY |
| Parquet: saved landmarks and segment poses | Imports SkellyForge landmarks and segment poses directly |
| Parquet: landmarks with Blender constraints | Uses landmark trajectories to drive the legacy Blender constraint reconstruction |
| Legacy NPY | Uses the original MediaPipe output files and Blender constraints |

Parquet input is tracker-independent once it has been mapped to the standard human
model. The Parquet recording must contain an unambiguous selected run and sensor
group. API callers may supply `runId`, `sensorGroup` and `trajectoryChannel`;
`MAPPED_KEYPOINTS_3D` is available for the constraint comparison route.

The export always saves a `.blend`. Optional FBX is available on all routes; BVH
requires legacy NPY. T/A rest poses and optional foot locking/hand motion limits
require a constraint route. The automatic route exposes conservative settings;
select a constraint route explicitly to enable cleanup. Additional formats default
to none, and cleanup defaults to off. The saved-segment route preserves recorded
poses. Unsupported requests fail rather than silently falling back.

Cleanup edits Blender animation targets, not the source Parquet. COM continues to
represent the original recording. The calibration/alignment persistence workflow
is a separate deferred issue; export does not try to correct calibration geometry.

Click **Process Recording with Blender**, or enable export after processing.
The backend confirms successful completion and a nonempty output before optionally
opening Blender. An old `.blend` cannot hide a subprocess failure.

## HTTP interface

Endpoints are under `/freemocap/blender`:

- `GET /detect`: locate a Blender executable.
- `POST /inspect`: inspect the selected runtime and enabled FreeMoCap packages.
- `POST /addon/install`: install an explicit `archivePath` into that runtime.
- `POST /export`: export `recordingFolderPath`, optionally selecting `route`,
  `package`, and `blenderExportConfig`.
- `POST /open`: open a previously exported scene.

`blenderExportConfig` retains main's flat fields: `formats`, `rest_pose`,
`apply_foot_locking`, and `limit_hand_markers_range_of_motion` (camelCase aliases
are also accepted). Core translates these to the add-on's nested sections.

## Development validation

The published add-on revision used for this integration is
`d0dd5ef745db6a6f7523acf333da6bf15c66ea32`. Core's lockfile and installed host
package were verified at that revision; actual exports use the installed Blender
package, not that host import.

On Windows, core HTTP tests passed installation, restart, exports and scene
reopening for both prepared datasets through both Parquet routes on Blender 3.0.0
(legacy package) and 5.2.2 (Extension). Constraint tests also exercised A-pose,
foot locking and FBX output. Source publication hashes remained unchanged.
Fourteen host export tests passed, plus thirteen related provenance/CSV tests.
Completion-handler coverage includes enabled/disabled exports, cancellation and
export failure while preserving the processing result. A browser test exercised package setup, route
capabilities and export request options with mocked HTTP responses. UI TypeScript
checking passed. The tests use disposable preferences and recording copies.

Local evidence is under `.test-artifacts/blender-core/`. Re-run host tests with:

```powershell
.venv/Scripts/python.exe -B -m pytest freemocap/tests/test_blender_export.py -p no:cacheprovider
```

For integration tests, set `FREEMOCAP_BLENDER_EXE` and `FREEMOCAP_BLENDER_ZIP`,
then run `freemocap/tests/test_blender_integration.py`. They use the core prepared
publication workflow and skip when the runtime/package variables are absent.

macOS/Linux runtime testing, a complete historical NPY recording and a full
interactive Electron session remain outside this measured coverage. Existing
Windows Extension DLL-cleanup warnings can require restarting Blender after
updating a loaded package.
